# 镜像名称链接与详情页删除弹框设计

## 背景

镜像列表当前以 `Tags` 作为首列标题，只有镜像 ID 可以进入详情。详情页的“删除可用 Tags”会先跳到独立预览页，提交后再跳到独立结果页，操作路径偏深。

本次调整把用户可识别的 Tag 统一称为“镜像名称”，让名称本身成为详情入口，并把删除预览、确认、执行结果集中到镜像详情页的原生弹框中。

## 范围

### 包含

- 镜像列表首列标题改为“镜像名称”。
- 每个镜像名称均可点击进入该不可变镜像 ID 对应的详情页。
- 无 Tag 的镜像显示可点击的短 ID，仍可进入详情。
- 详情页中的 `Tags` 文案改为“镜像名称”。
- 详情页删除按钮改为打开原生 `<dialog>`，不再导航到删除预览页。
- 弹框展示当前可删除名称、因容器引用而保留的名称以及 Docker 无 CAS 的并发风险提示。
- 确认后通过同源 API 异步删除，当前页面 URL 不变。
- 删除成功后在弹框内展示实际删除、保留、跳过的名称和镜像是否仍存在。
- 镜像仍存在时，重新读取详情 API 并同步详情页中的名称；镜像已不存在时，禁用删除入口并提供“返回镜像列表”。
- 请求失败时在弹框中展示服务端错误，保持弹框和当前详情页。
- 无 JavaScript 时，表单通过 Web POST 完成同一删除动作并 `303` 回到镜像详情或镜像列表，不进入独立结果页。

### 不包含

- 不改变 Tag 使用判断、逐 Tag 重新解析、非强制删除或并发安全语义。
- 不改变镜像分页、搜索、inspect 或容器引用逻辑。
- 不新增整镜像强制删除。
- 不在列表页直接提供删除按钮。

## 页面设计

### 镜像列表

首列表头为“镜像名称”。有一个或多个 Tag 时，每个 Tag 单独渲染为链接，目标统一为 `/images/<完整镜像 ID>`。这样多名称镜像的每个可见名称都能作为详情入口。

无 Tag 镜像不再只显示不可点击的“未标记”，而是显示短 ID 链接，并附带“未标记”提示。镜像 ID 列继续保留原有详情链接，作为稳定的技术标识入口。

### 镜像详情

标题优先显示首个镜像名称，无 Tag 时显示短 ID。定义列表中的 `Tags` 改为“镜像名称”。删除入口为 `type="button"`，通过 `data-dialog-open` 打开页面内固定 ID 的删除弹框。

弹框初始状态包含：

- “将删除的镜像名称”列表；
- “因容器正在使用而保留的镜像名称”列表；
- Docker 不支持条件删除 Tag 的并发窗口提示；
- 关闭按钮与确认删除按钮。

仅当存在可删除名称时显示可用的确认按钮。页面加载时已有的服务端预览只是操作前说明；删除服务仍会在提交时重新读取容器和 Tag 状态，不能把该预览当作授权或删除清单。

## 数据流

1. `GET /images/<id>` 同时读取镜像详情和 Tag 删除预览，并把完整预览传给模板。
2. 用户打开弹框时不发起请求，直接展示服务端渲染的预览。
3. 用户确认后，JavaScript 拦截弹框表单，向 `DELETE /api/images/<id>/tags` 发同源请求。
4. API 调用现有 `remove_available_tags()`；服务在不可变完整 ID 的进程锁内重新计算并逐 Tag 校验。
5. 成功响应中的 `deleted_tags`、`retained_tags`、`skipped_tags` 和 `image_exists` 原地渲染到弹框。
6. 若 `image_exists=true`，前端再调用 `GET /api/images/<id>` 获取权威的当前名称并更新详情页名称区域；刷新失败不撤销已展示的删除结果，只显示“详情同步失败，可手动刷新”。
7. 若 `image_exists=false`，详情页标记镜像已删除，隐藏或禁用删除按钮，并在弹框提供返回 `/images` 的入口。

## 无 JavaScript 降级

弹框内确认控件保留普通 `POST /images/<id>/delete` 表单。服务端完成删除后：

- 镜像仍存在：`303` 到 `/images/<id>`；
- 镜像已不存在：`303` 到 `/images`。

降级路径不使用独立预览页或结果页。错误继续使用现有 404、409、503 HTML 错误页。

旧的 `GET /images/<id>/delete` 和结果页路由不再由 UI 引用；为避免已有书签突然失效，GET 预览路由改为 `307` 返回详情页。进程内旧结果 URL 可以保留兼容读取，但不再产生新的结果记录。

## 安全与错误处理

- 删除仍使用现有同源安全中间件，跨源 `DELETE` 和 `POST` 保持 403。
- JavaScript 使用 `encodeURIComponent` 编码镜像 ID，并只向本服务固定 API 路径发送请求。
- 页面内容继续依赖 Jinja2 自动转义；异步结果使用 `textContent`，不拼接不可信 HTML。
- 404 表示镜像在操作前已不存在；409 表示提交时没有可删除名称；503 表示 Docker daemon 或 SDK 失败。
- 弹框请求期间禁用确认按钮，防止同一页面重复提交；请求结束或失败后恢复适当状态。

## 测试

- Web 测试验证列表表头为“镜像名称”，Tag 与无 Tag 短 ID 都链接到完整 ID 详情。
- Web 测试验证详情页内包含删除 `<dialog>`、预览内容、普通降级表单，且删除按钮不是导航链接。
- Web 测试验证 POST 降级路径根据 `image_exists` 回到详情或列表，不创建结果页跳转。
- JavaScript 契约测试验证同源 DELETE、请求期间禁用、结果字段渲染、当前名称同步以及错误文本渲染。
- API 与服务层已有测试继续覆盖容器使用判断、重新解析、跳过重指/消失 Tag、Docker 错误和跨源拒绝。
- 全量测试、JavaScript 语法检查、wheel 模板资源检查和 Compose 配置检查作为交付门槛。
