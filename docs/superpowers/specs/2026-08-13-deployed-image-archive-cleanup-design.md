# 已部署任务镜像归档清理设计

## 背景与目标

每次上传离线部署包时，服务端会在任务目录保存原始 `archive.tar.gz`，并将其解压到 `extracted/`。部署时又会把解压内容覆盖到稳定部署目录。因此，一次包含离线镜像的成功部署通常留下三份大体积镜像归档：

- `packages/<任务 ID>/archive.tar.gz` 中包含的 `images.tar`；
- `packages/<任务 ID>/extracted/images.tar`；
- `deployments/<app_name>/images.tar`。

成功部署完成后，Docker 已经加载镜像，Compose 也已经创建并启动容器，这三份镜像归档不再参与当前运行。与此同时，历史任务自己的 `compose.yaml`、`.env` 和其他小文件仍有配置审计、版本比对价值，不能改为读取会被后续同名部署覆盖的稳定部署目录。

本次增加成功部署后的辅助清理：删除三份镜像归档，保留每个历史任务自己的配置快照，并保证任何清理问题都不污染部署主状态。

## 范围

### 包含

- 只对功能上线后新完成的成功部署执行清理。
- 只有镜像加载和 `docker compose up -d` 都成功，并且 `deployed` 主状态已经持久化后才开始清理。
- 删除本次任务的原始上传归档、任务解压目录中的镜像归档，以及当前应用稳定部署目录中的镜像归档。
- 保留任务解压目录中的 `compose.yaml`、`.env`、`manifest.json`、`checksums.sha256` 和其他非镜像归档文件。
- 任务详情继续读取该历史任务自己的 `extracted/`，展示部署当时的配置，而不是稳定部署目录中的最新配置。
- 逐项记录清理时间和警告；单项失败不阻止其他项清理，也不改变 `deployed` 状态。
- 在任务详情中展示镜像归档清理结果。

### 不包含

- 不扫描或自动清理功能上线前已经存在的历史任务。
- 不增加定时清理、按天数过期、磁盘阈值清理或服务启动时清理。
- 不自动清理失败、待审核、正在部署或其他非成功终态任务。
- 不删除历史任务的配置快照、任务 JSON、命令输出或稳定部署目录中的运行数据。
- 不删除 Docker 中已经加载的镜像、容器、网络或数据卷。
- 不改变现有失败任务的手动丢弃与重试语义。

## 清理时机与主业务隔离

部署主流程按以下顺序执行：

1. 将任务解压目录覆盖合并到稳定部署目录。
2. 按现有规则准备挂载目录及权限。
3. 从稳定部署目录执行 `docker load -i images.tar`。
4. 从稳定部署目录执行 `docker compose up -d`。
5. 将任务主状态设置为 `deployed` 并先持久化。
6. 调用独立的镜像归档清理函数。
7. 将清理时间与清理警告作为辅助信息再次持久化。

第 5 步必须先于任何删除动作。若主状态持久化失败，不执行清理，保留完整任务文件供现有恢复流程处理。若进程在主状态持久化后、清理完成前退出，本次不做启动补偿或后台重扫；可能残留镜像归档，但不会损坏已部署服务或历史配置。

清理阶段不是部署成功条件。删除失败、清理结果持久化失败或页面展示异常都不得把任务改为 `failed`，也不得覆盖部署命令输出和已有错误字段。服务返回的任务仍为 `deployed`。

## 精确删除范围

清理函数仅处理以下三个固定目标：

1. `TaskStore.package_dir(task_id) / "archive.tar.gz"`；
2. `TaskStore.extracted_dir(task_id) / "images.tar"`；
3. `TaskStore.deployment_dir(app_name) / "images.tar"`。

路径根据已经验证的 `task_id` 和 `app_name` 通过 `TaskStore` 重新计算，不接受请求参数提供的文件路径，也不直接信任任务 JSON 中可变的绝对路径字段。删除前验证每个目标的父级归属：前两个目标必须位于该任务自己的包目录内，第三个目标必须位于该应用自己的稳定部署目录内。

删除只针对精确文件，不使用递归删除，不扫描同名文件，不跟随符号链接。目标不存在视为该项已经清理，不产生警告，以便单次清理过程具备幂等性。目标是目录、符号链接或其他非普通文件时拒绝删除并记录警告。

应用级清理继续位于现有 `app_name` 锁内，避免同一应用并发部署时，一个任务删除另一个任务刚覆盖到稳定目录的 `images.tar`。

## 数据模型与兼容性

`DeploymentTask` 增加两个可选辅助字段：

- `image_archive_cleanup_at: datetime | None`：本次成功部署完成镜像归档清理尝试的时间；
- `image_archive_cleanup_warnings: tuple[str, ...]`：未能清理的目标标识及安全错误摘要，默认空元组。

`image_archive_cleanup_at` 表示清理尝试已经结束；警告为空表示三个目标均已删除或原本不存在，警告非空表示部分清理。警告使用稳定目标标识，例如“原始上传包”“任务镜像归档”“稳定部署镜像归档”，避免将任意外部输入直接写入页面。

旧任务 JSON 缺少这些字段时按 `None` 和空元组加载，不触发补清理。任务主状态、失败阶段、部署错误与命令输出的含义保持不变。

保留的 `manifest.json` 和 `checksums.sha256` 描述原始离线包，因此其中仍可能声明已经清理的 `images.tar`。系统不在历史详情加载时重新按该校验文件验证已清理后的任务目录；页面明确说明镜像归档在部署成功后已回收，避免将这一预期差异误认为文件损坏。

## 历史任务详情

部署任务详情保持以 `packages/<任务 ID>/extracted/` 为数据源：

- `compose.yaml` 和 `.env` 展示该任务部署时保存的历史版本；
- 文件清单展示清理后实际仍存在的任务文件；
- 不切换到 `deployments/<app_name>/`，因此后续同名应用再次部署不会改写旧任务详情；
- 清理尝试完成且无警告时显示“镜像归档已清理”及时间；
- 存在警告时显示“镜像归档部分清理”，并列出未清理目标和安全错误摘要；
- 旧任务未执行过该功能时不显示“已清理”，也不暗示其镜像归档不存在。

部署失败和待审核任务仍保留完整上传包及解压内容，详情、配置编辑和重试继续使用现有路径。用户需要释放失败任务空间时，继续使用现有“丢弃”操作。

## 异常处理

清理函数逐项执行并捕获每个目标的 `OSError` 及文件类型异常：

- 某项删除失败时追加一条警告，继续处理其余目标；
- 全部目标处理完成后统一返回清理结果，不抛出表示部署失败的异常；
- 清理结果保存失败时不回滚已经删除的文件，不修改已经持久化的 `deployed` 主状态；
- 服务端记录清理结果保存失败，当前请求仍按已部署结果结束。

清理逻辑不修改 `task.error`，避免辅助警告与部署错误共用同一字段。它也不修改 `command_output`，因为文件删除不是 Docker 部署命令的一部分。

## 测试策略

### 服务层

- 成功部署后删除原始上传归档、任务 `extracted/images.tar` 和稳定部署目录 `images.tar`。
- 成功部署保留任务自己的 `compose.yaml`、`.env`、manifest、校验文件和其他小文件。
- `docker load` 失败时三处文件全部保留，任务按现有规则进入部署失败。
- `docker compose up -d` 失败时三处文件全部保留，任务按现有规则进入部署失败。
- 主状态首次持久化失败时不执行清理。
- 单项目标删除失败时继续删除另外两项，最终任务仍为 `deployed`，并记录对应警告。
- 目标不存在按成功处理；目标是目录或符号链接时不删除并记录警告。
- 路径只从安全的任务 ID 和应用名重新计算，不能删除任务目录或应用部署目录之外的文件。
- 同一应用的清理在应用锁内完成。
- 清理辅助结果的持久化失败不改变已经保存的 `deployed` 状态。

### 存储与兼容性

- 新字段能够保存并重新加载。
- 缺少新字段的旧任务 JSON 使用默认值加载。
- 读取旧任务不会触发文件删除。

### Web 与 API

- 已清理任务详情继续展示任务自己的历史 `compose.yaml` 和 `.env`。
- 清理完整时展示完成时间，部分清理时展示安全警告。
- 未执行清理的旧任务和未成功任务不显示错误的清理完成状态。
- 文件列表不再包含已删除的 `images.tar`，但仍包含保留的小文件。
- 现有部署、编辑配置、重试、丢弃和任务查询行为保持兼容。

## 交付验证

交付前运行部署服务、存储、API 和 Web 相关测试，再运行完整测试套件。构建 wheel 后检查模板和服务端代码均已打包，并使用一个包含镜像归档的测试任务验证：部署成功、容器正常运行、三份镜像归档消失、历史配置仍可查看，且再次部署同名应用不会改变旧任务详情中的配置快照。
