# 部署配置编辑与目录准备设计

## 背景与目标

Docker Manage Server 当前会在离线包上传并解压后展示文件树、`.env` 和 `compose.yaml`，但审核内容只能查看。打包错误、部署环境差异或临时配置调整都要求用户回到客户端重新打包。服务端虽然能够根据 `manifest.server_paths` 创建缺失的相对 `files/...` 目录，但目录权限固定为 `0777`，页面也不能添加 Compose 新引用的部署目录。

本次功能让用户在部署前编辑解压工作区中的 `.env` 与 `compose.yaml`，并维护一组部署目录准备规则。每条规则包含部署根目录内的安全相对路径和 Linux 标准权限。规则在部署时创建缺失目录，或更新显式指定的已有目录本身权限，从而避免 Docker Compose 自动创建出不可写目录。已经成功解压但部署失败的任务也可以编辑并重新部署。

本次不提供任意文件编辑器、绝对宿主机路径管理、递归权限修改、所有者修改或部署失败自动回滚。

## 核心流程

1. 离线包上传、解压并通过原有完整性校验后进入待审核状态。
2. 用户从任务详情页进入独立的“编辑部署配置”页面。
3. 用户编辑 `.env`、`compose.yaml`，并添加、修改或删除“相对目录路径 + 权限”规则。
4. 服务端校验候选文本、Compose 配置、目录路径和权限。全部通过后才更新解压工作区和任务状态。
5. 保存成功后任务进入待审核状态，当前错误被清除，既有命令输出继续保留用于排查。
6. 用户点击部署或重新部署后，服务端先把解压工作区覆盖合并到稳定部署目录，再应用目录准备规则，最后执行镜像加载和 `docker compose up -d`。
7. 任一步骤失败时任务进入失败状态并记录失败阶段和具体错误。部署阶段失败的任务可以继续编辑或直接重试。

编辑和规则保存不会提前修改稳定部署目录。稳定目录只在用户明确部署时发生变化。

## 状态与数据模型

新增目录规则模型：

```text
DirectoryRule
  path: string       # 规范化后的 POSIX 相对路径
  mode: string       # 四位八进制字符串，例如 0775
```

部署任务新增以下可选字段，并为旧任务提供兼容默认值：

- `directory_rules`：任务的完整目录准备规则；`null` 表示旧任务尚未迁移，部署或编辑展示时从安全的相对 `server_paths` 转换，权限默认为 `0777`；空列表表示用户明确删除全部规则。
- `failure_phase`：`upload` 或 `deploy`，用于区分不可恢复的上传/解压失败与可编辑、可重试的部署失败。
- `edited_at`：最近一次人工保存配置的时间；未编辑时为空。

新上传任务会立即把 `manifest.server_paths` 中安全的相对路径转换成目录规则。绝对 `server_paths` 保持现有兼容语义，不由服务端自动创建或修改权限，也不显示为可编辑目录规则。

任务满足以下全部条件时属于“可恢复的部署失败”：

- 状态为 `failed`；
- `failure_phase` 为 `deploy`，或旧任务缺少该字段但已经具有安全的应用名、部署目录以及完整的解压工作区；
- 解压工作区中存在 `.env` 和 `compose.yaml`。

待审核任务和可恢复的部署失败任务可以编辑。部署接口接受待审核任务和可恢复的部署失败任务。上传中、解压中、正在部署、已部署、已丢弃以及不可恢复的上传失败任务均不可编辑或重试。

## 服务边界

部署服务新增三个职责清晰的操作：

1. **读取可编辑配置**：返回当前 `.env`、Compose 原文和已解析的目录规则。
2. **校验并保存配置**：在任务锁内二次检查状态，校验全部候选内容，以全有或全无方式更新工作区文件、校验和及任务状态。
3. **应用目录规则**：在覆盖合并完成后、Docker 命令执行前，安全创建目录并对规则目标本身执行 `chmod`。

保存与部署共享任务级互斥边界，应用部署继续使用现有应用级锁。任何请求在等待锁期间若任务状态发生变化，进入临界区后必须重新校验，不能依赖锁外读取的状态。

## 页面设计

### 任务详情页

- `.env` 和 `compose.yaml` 保持只读预览。
- 新增“部署目录准备”区域，逐行显示相对路径、八进制权限和当前目标状态：尚未创建或已存在。
- 待审核任务显示“编辑配置”和“确认部署”。
- 可恢复的部署失败任务显示“编辑并重试”和“重新部署”。
- 其他状态不显示编辑或重试入口。
- 人工编辑过的任务显示最近编辑时间。

### 编辑页

- `.env` 和 `compose.yaml` 分别使用大文本编辑框。
- 目录规则以可增删的行展示，每行包括相对路径、常用权限预设、精细权限展开区、四位八进制结果和删除操作。
- 常用预设包括 `0700`、`0750`、`0755`、`0770`、`0775` 和 `0777`，并显示简短中文用途说明；`0777` 显示安全提醒。
- 精细权限区提供所有者、用户组和其他用户各自的 `r/w/x` 勾选项，勾选变化与八进制值双向同步。
- 页面提供“保存并校验”和“取消”。不提供递归修改权限选项。
- 保存失败时保留用户输入，在对应区域展示错误，并保证服务端当前有效配置不变。

前端脚本只负责规则行增删、预设和 `r/w/x` 转换以及提交字段整理。权限和路径安全仍由服务端完整复验。

## API 与 Web 路由

新增路由：

```text
GET  /deployments/{task_id}/edit
POST /deployments/{task_id}/edit
PUT  /api/deployment-tasks/{task_id}/configuration
```

Web POST 接受表单并在失败时重新渲染编辑页。JSON API 接受：

```json
{
  "env": "...",
  "compose": "...",
  "directories": [
    {"path": "data/mysql", "mode": "0770"}
  ]
}
```

现有 review API 增加以下字段：

- `directories`：规范化目录规则及目标存在状态；
- `editable`：当前任务能否编辑；
- `retryable`：当前任务能否部署或重新部署；
- `edited_at`：最近编辑时间。

现有 Web 和 API deploy 路由继续返回原有状态码语义，但允许可恢复的部署失败任务重新进入部署流程。失败任务开始重试时清除当前错误并把状态置为 `deploying`；保存成功时状态置为 `pending_review`。

所有新增非安全方法继续经过现有同源安全边界。

## 内容校验与一致性

### 文本与 Compose

- `.env` 和 Compose 必须是 UTF-8 文本，并分别设置明确的请求大小上限；超过限制返回 `413`，不进入候选校验或写入。
- 候选文件先写入解压工作区内的受控临时文件。
- 使用服务器现有 Docker Compose CLI，以解压工作区为 project directory，并显式指定候选 Compose 与候选 env 文件执行 `docker compose config --quiet`。
- Compose 校验错误原样保留关键上下文，但页面输出仍通过模板自动转义。
- 只有 Compose 校验、路径校验和权限校验全部成功后，才替换正式 `.env` 与 `compose.yaml`。

保存操作保留旧 `.env`、Compose、`checksums.sha256` 和任务状态作为回滚快照。任何文件替换、校验和生成或任务持久化失败时，恢复快照并返回错误，确保不会出现半套配置。

保存成功后重新计算解压工作区中全部受校验普通文件的摘要并生成 `checksums.sha256`。原始 `archive.tar.gz` 永远不修改，继续作为上传内容的审计来源。

### 目录路径

用户输入先按 POSIX 相对路径规范化，去除多余的 `.` 段和前导 `./`。以下输入被拒绝：

- 空字符串、`.`、绝对路径、反斜杠、NUL 或任何 `..` 段；
- 规范化后越出当前应用稳定部署根目录的路径；
- 任一路径组件是符号链接；
- 目标或中间组件与已有普通文件冲突；
- 同一规范化路径出现多次。

路径可以位于部署根目录下的任意层级，例如 `data/mysql`、`logs/nginx` 或 `files/sqlite`，不再局限于 `files/`。

### 权限

- API 和持久化层只接受四位字符串 `0000` 至 `0777`，不接受符号模式、负数或特殊权限位。
- 服务端把权限解析为整数并直接调用文件系统 `chmod`，不拼接 shell 命令。
- 目标不存在时使用 `mkdir(parents=True)` 创建，再对规则指定的最终目录本身设置权限。
- 目标已经存在且为真实目录时，仍对该目录本身应用规则权限，以修复 Compose 已自动创建出的错误权限。
- 不递归修改目标内部文件或子目录，不执行 `chown`，也不跟随符号链接。
- 多级路径中由本次 `mkdir(parents=True)` 隐式创建的父目录使用服务端默认安全目录权限；只有规则明确列出的目录获得其指定模式。用户需要控制父目录模式时，应为父目录单独添加规则。

## 部署顺序与失败语义

一次部署或重试严格按以下顺序执行：

1. 将解压工作区覆盖合并到稳定部署目录，保留现有“不删除归档中缺失文件”的语义。
2. 逐条校验稳定目录的真实路径状态，拒绝部署期间新出现的符号链接或文件冲突。
3. 创建缺失目录并修改每个规则目标本身权限。
4. 如果存在 `images.tar`，执行 `docker load`。
5. 在稳定部署目录执行 `docker compose up -d`。

目录创建或 `chmod` 失败时停止后续 Docker 命令，任务记录 `failure_phase=deploy`、具体路径和系统错误。Docker 命令失败同样进入可恢复的部署失败状态。

本次不实现自动回滚。覆盖合并、目录创建、权限变更或 Docker 操作已经产生的效果会保留。用户修正配置后再次部署，继续使用相同稳定目录和覆盖合并语义；服务端不会删除已有应用数据。

## 测试策略

### 单元测试

- 相对路径规范化及空值、绝对路径、反斜杠、NUL、`..`、重复项拒绝。
- 符号链接越界、任意符号链接组件和普通文件冲突拒绝。
- 常用预设、`r/w/x` 与四位八进制转换以及非法权限拒绝。
- 新目录按规则创建，已有目录权限被更新，目录内容权限保持不变。
- 多级路径只对显式规则目标应用指定权限。
- 候选 Compose 校验失败时工作区文件、校验和和任务状态完全不变。
- 保存中途失败时快照恢复；成功时两个配置文件、规则、编辑时间和校验和一致更新。
- 待审核和部署失败状态允许编辑；其他状态拒绝。
- 旧任务的 `server_paths` 兼容转换，且显式空 `directory_rules` 不会重新引入旧规则。

### API 与 Web 测试

- 编辑页在允许和禁止状态下的可见性与响应码。
- Web 表单成功、Compose 错误、路径错误、权限错误和超限请求。
- JSON API 的请求与返回结构、错误状态和 HTML 注入转义。
- review API 返回目录规则、目标状态、`editable`、`retryable` 和 `edited_at`。
- 部署失败任务可以保存后部署，也可以不修改直接重试；上传失败任务不可重试。
- 新增写接口继续拒绝跨源请求。

### 部署与回归测试

- 断言覆盖合并后、镜像加载和 Compose 启动前已经完成目录创建和 `chmod`。
- 模拟 Compose 自动创建的 `0755` 目录，重试时按显式规则修正权限且不修改内部文件模式。
- 目录准备失败不会执行 Docker 命令，并产生可恢复的部署失败任务。
- 运行部署、归档、API、Web、安全和容器管理完整测试套件。
- 运行 `docker compose config` 验证服务自身部署配置。

## 成功标准

- 用户无需重新制作离线包即可安全修改 `.env` 和 `compose.yaml`。
- 用户可以为部署根目录内任意安全相对目录配置标准 Linux 权限。
- 新建目录和明确指定的已有目录在 Compose 启动前获得目标权限，内部数据不被递归修改。
- 已成功解压但部署失败的任务可以编辑并重新部署，也可以原样重试。
- 校验失败或并发状态变化不会留下部分保存的配置。
- 原始上传归档保持不变，旧任务和旧离线包继续可用。
